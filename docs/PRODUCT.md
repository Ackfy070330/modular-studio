# 产品方案

版本：0.1 / 2026-10-12 / 待开发。

## 1. 产品定位

帮助用户用模块表达软件意图，由智能体完成受约束的代码开发，并在运行后沿着真实数据流理解和修复软件。

建议首先服务独立开发者和小型开发团队：他们能运行前后端项目，但希望减少需求描述、代码理解和跨端排错的成本。非技术用户可以从模板开始使用；完全零编程的任意软件开发留待模块库和错误提示成熟后扩展。

最核心的价值是：用户指着一个模块就能知道“它应该做什么、由哪些代码实现、这次实际做了什么”，并能把同一上下文交给智能体修改。

## 2. 一个项目的三个视图

| 视图 | 回答的问题 | 内容来源 | 是否可编辑 |
| --- | --- | --- | --- |
| 功能蓝图 | 我希望软件做什么？ | 用户积木、契约、验收条件 | 可以，产生蓝图新版本 |
| 实现结构 | 代码现在如何组织和调用？ | 源码分析、框架规则、用户映射 | 可以标注和修正映射；代码变化后重新分析 |
| 运行数据流 | 某次执行实际发生了什么？ | 采集的轨迹、业务数据快照、调试会话 | 原始记录不可修改，可筛选和注释 |

三个视图共享模块目录和源码关联，但不强制节点一一对应。一个产品模块可能对应多个函数；同一个函数也可能参与多个产品功能。

导入项目最初可以只有实现结构和运行数据流。用户确认模块分组后，再逐步整理成可编辑的功能蓝图。

## 3. 功能一：Scratch 式模块化设计与智能体协作

### 3.1 两层编辑方式

外层是产品模块画布，用于表达页面、事件、接口、业务规则和数据存储之间的关系。内层是积木编辑器，用于表达某个模块内的条件、顺序、校验、计算和错误处理。

例如，一个“订单提交”功能可以展开为：

```mermaid
flowchart LR
    A[订单表单] -->|点击提交 / 订单数据| B[创建订单 API]
    B --> C[校验订单]
    C --> D[计算金额]
    D --> E[保存订单]
    E --> F[返回订单结果]
    F --> G[显示订单回执]
```

“计算金额”模块内部则是：读取单价与数量 → 相乘 → 应用折扣规则 → 输出总金额。用户可以把这个组合保存成可复用模块。

页面模块需要有表单字段、按钮和显示区域等配置。首版提供几种表单/列表/详情模板，保证蓝图可以生成可使用的前端；自由排版的页面设计器作为后续能力。

### 3.2 首批模块库

| 类别 | 首版内容 | 主要配置 |
| --- | --- | --- |
| 页面 | 表单、列表、详情、结果提示 | 字段、校验、绑定数据、交互事件 |
| 事件 | 点击、提交、页面加载 | 触发源、输入、后续动作 |
| 接口 | HTTP 请求、HTTP 路由、返回结果 | 方法、路径、请求与响应结构 |
| 逻辑 | 条件、顺序、字段校验、计算、错误分支 | 表达式、输入输出、分支条件 |
| 数据 | PostgreSQL 表、查询、插入、更新 | 数据模型、参数、约束 |
| 扩展 | 自定义代码模块 | 接口契约、源码入口、测试要求 |

鉴权、事务、队列、定时任务和跨服务编排先在模型中留出类型，后续逐项实现。首版处理受限的有序业务流程；显式循环、并行汇合和补偿事务需要独立的执行语义。

### 3.3 每个模块必须表达的内容

- 名称与职责：用业务语言说明做什么。
- 输入与输出：字段、类型、必填性、错误结构。
- 约束：权限、校验规则、幂等需求，以及适用的运行位置。
- 验收条件：例如“单价 100、数量 2 时，总金额为 200”。
- 实现绑定：关联源码符号与版本，生成模块还记录模板或生成器版本。
- 运行观察：需要记录哪些字段、哪些字段屏蔽、允许在哪些环境采集。

页面坐标和颜色只是呈现信息，不能决定模块的业务行为。

### 3.4 智能体协作流程

1. 用户选中一个模块或一组模块，输入修改目标。
2. 工作台打包相关蓝图片段、接口契约、依赖、源码和验收条件；排除不需要的文件与数据。
3. 智能体返回实现计划，并在隔离的工作副本中开发。
4. 工作台展示文件差异、受影响模块、运行结果和测试结果。
5. 用户可以接受、局部接受或要求修改；应用时核对原始代码版本，避免覆盖并行编辑。
6. 测试通过并应用代码后，更新源码绑定和实现结构。用户可继续启动项目，在图上查看真实运行数据。

设计时可使用“未实现、实现中、待验证、已验证、发生漂移”等状态；运行状态单独使用“执行中、成功、异常、未观察到”。智能体声称完成不能自动把模块标为已验证。

### 3.5 厂家中立的接入产品形态

| 用户已有能力 | 工作台接入方式 | 能保证到哪一步 |
| --- | --- | --- |
| 支持 ACP 的编程智能体 | 工作台作为客户端连接 | 以协商出的会话、工具和取消能力为准 |
| 只支持 MCP 的智能体客户端 | 工作台向其提供蓝图、源码和诊断工具 | 客户端可以调用工具；工作台未必能主动调度其完整会话 |
| 提供 SDK、HTTP API 或 CLI 的智能体 | 专用适配器 | 按该适配器实际通过的功能测试展示能力 |
| 只有模型推理 API | 自建带文件、测试等工具的执行循环 | 这是工作台提供的智能体执行能力，需要单独开发 |
| 没有开放接口 | 导出任务包、手动回导修改 | 标为手动协作，不能显示为自动接入 |

兼容列表按能力展示，如“读代码、提交变更、运行测试、取消任务、恢复会话”。首版至少验收一个真实编程智能体适配器，不能用模型选择下拉框或模拟响应替代。

## 4. 功能二：导入项目、数据流与调试

### 4.1 导入流程

用户选择本地项目 → 连接器读取项目清单 → 识别语言和框架 → 生成结构图 → 展示识别范围和未知关系 → 用户确认模块映射 → 选择运行配置 → 加入采集配置并启动。

导入分析本身只读取代码。依赖安装、运行脚本、注入采集或执行调试是后续的明确动作。

首版识别 React/Vite 前端与 Node.js/Fastify 后端中受支持的路由声明、显式请求、函数调用和 PostgreSQL 访问模式。动态路由、反射、复杂依赖注入、未支持 ORM 和外部黑盒服务应保留为未知或边界节点。

### 4.2 “完整流向”的产品定义

目标是提供已接入范围内尽可能完整、可解释的观察，而不是声称仅凭源码就能穷尽任意程序的所有行为。

系统区分三种关系：

| 关系 | 例子 | 证据 |
| --- | --- | --- |
| 结构依赖 | 页面引用某个请求函数 | 源码可定位的导入或调用 |
| 执行关系 | 某次请求执行了校验和存储 | 运行轨迹和显式上下文关联 |
| 数据变换 | quantity 如何参与 total 的计算 | 字段映射、受控逻辑描述或专门采集 |

调用先后和父子 Span 关系不自动证明字段如何变换。字段级追踪首版覆盖受控积木与显式声明的映射；任意导入代码中的字段血缘属于后续分析能力。

每条关系显示来源：源码解析、规则推断、用户确认或运行观察。未执行路径显示“本次未观察到”；数据缺失显示“未采集/已截断/已脱敏/关联中断”，不能显示为成功或零值。

覆盖范围报告至少列出发现的服务、已接入采集的服务、未知调用、断开的 Trace 上下文和当前采样策略。比例指标必须注明分母及统计窗口，不能称作任意程序的全量覆盖率。

### 4.3 每次执行可以看到什么

- 路径：浏览器事件 → 网络请求 → 后端处理 → 数据库/外部服务 → 响应 → 页面更新。
- 节点：开始结束时间、耗时、状态、错误、相关日志和源码位置。
- 数据：采集策略允许的输入、输出、字段差异和业务快照；大对象按深度/大小截断。
- 环境：开发/测试/生产标签、服务、实例、代码版本、构建版本、运行时间。
- 上下文：Trace ID、Span ID、请求关联标识，以及调试器在暂停点可获取的变量与调用栈。

开发、测试、生产是不同的运行环境；一次请求通常发生在一个环境中。画布可以比较多个环境，但不能默认把它们画成请求依次经过的三个节点。真实跨环境访问需要独立标记。

环境配置面板只展示允许查看的配置摘要，例如服务地址、运行模式和版本；密钥及环境变量全集不作为默认展示内容。

### 4.4 两种调试模式

| 模式 | 可以做什么 | 依赖与限制 |
| --- | --- | --- |
| 轨迹检查与回放 | 沿已记录步骤查看数据、耗时、异常和源码，比较成功/失败执行 | 回放不再次发出请求，也不能查看未记录变量 |
| 实时调试 | 在源码位置或可映射模块设断点，暂停/继续/单步，展开局部变量和调用栈 | 需要对应语言的调试适配器、可调试目标与有效源码映射 |

首版实际断点支持本地 Node.js，优先保证变量和调用栈可用。浏览器端先支持事件/请求/结果采集与源码跳转；浏览器实时断点作为下一里程碑，路线与后端共用调试面板。

模块断点需要映射为一个或多个真实源码位置。映射失效时显示“待重新绑定”，不能伪造已生效状态。一次服务暂停并不意味着分布式系统全部暂停，其他服务超时应单独呈现。

生产环境优先只读观察与脱敏记录；开发/测试环境提供受控的交互调试。历史请求的“重新执行”独立于回放，需要单独设计副作用与幂等处理，首版不纳入。

### 4.5 智能体辅助排错

用户框选异常节点 → 选择要共享的轨迹和源码 → 智能体分析“期望值与实际值的差异” → 给出解释、修改和回归测试 → 用户查看差异 → 在测试环境重跑 → 对比新旧结果。

运行数据并不自动发送给智能体供应商。任务上下文明确列出包含的文件和经过筛选的字段；敏感字段在采集端先处理。

## 5. 主界面建议

```text
┌ 项目 / 版本 ── 设计 · 实现 · 运行 ── 环境 ── 启动 / 调试 ┐
│ 模块库 / 项目树 │                                       │
│ 页面、事件     │         当前视图的模块画布              │
│ 接口、逻辑     │         分组、展开、连线、路径高亮      │
│ 数据、自定义   │                                       │
├────────────────┴──────────────────────┬────────────────┤
│ 请求列表 / 时间线 / 日志 / 测试结果     │ 选中模块详情   │
│                                       │ 契约 / 数据    │
│                                       │ 源码 / 变量    │
└───────────────────────────────────────┴────────────────┘
智能体作为可收起侧栏，使用当前选中模块的上下文。
```

设计模式强调模块与验收条件；运行模式强调请求、环境、数据与时间。状态使用文字和图形共同表达，不能只依赖颜色。大图先按服务和模块分组，选中后逐层展开。

## 6. 首版验收场景

### 场景 A：从蓝图生成一个功能

拖入订单表单、创建订单接口、校验、计算金额、保存订单和回执模块 → 配置字段及连接 → 选择真实智能体 → 生成前后端代码和测试 → 查看变更 → 运行页面并提交订单。

通过条件：蓝图可保存重载，生成的软件能实际请求后端并写入测试数据库；测试验证关键业务规则；运行数据能映射回蓝图模块。

### 场景 B：导入已有项目并修复金额错误

导入受支持的订单项目 → 展示实现结构 → 启用采集 → 提交单价 100、数量 2 的订单 → 查看错误总额 100 → 在“计算金额”模块看到输入与输出 → 本地断点检查 quantity → 交给智能体补上乘法 → 测试得到 200。

通过条件：轨迹来自真实执行；前后端上下文可关联；断点真实命中；变量可读取；失败与修复后的记录保留各自的代码版本。单纯播放模拟数据不算场景通过。

## 7. 第一版范围与后续扩展

| 领域 | 第一版承诺 | 后续扩展 |
| --- | --- | --- |
| 产品设计 | 模块画布、受限逻辑积木、表单模板、版本保存 | 自由页面设计、模块市场、复杂控制流 |
| 智能体 | 统一任务协议 + 一个真实适配器 + 手动任务包 | 更多供应商、MCP 工具入口、远程协作 |
| 导入 | React/Vite + Fastify 的明确支持模式 | Express、Next.js、Python、Java、Go 等插件 |
| 数据流 | HTTP 链路、关键业务节点输入输出、数据库访问摘要 | 消息队列、跨语言、更多字段血缘 |
| 环境 | 多环境标识和筛选；开发环境实际接入 | 远程测试/生产采集、权限与审计完善 |
| 调试 | 本地 Node.js 断点/单步/变量；轨迹回放 | 浏览器实时调试、其他语言适配器 |

本方案以单人本地闭环开始，部署形态保留团队扩展接口。目标用户、首批框架和是否优先团队协作可在实现前进一步调整，不影响先验证两条核心旅程。
